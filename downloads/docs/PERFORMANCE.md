# Precompilation, scale and maintenance

## What visitors load

Leaderboard and record-detail pages are precompiled HTML. `npm run build` reads the local BibTeX/JSON, validates references, groups results, calculates ranks and strict historical improvements, and emits complete list/detail/navigation pages. Those pages need no initial manifest request, category descriptor request, record-page fetch, browser bibliography parser or client-side database query.

| Visitor action | Response |
| --- | --- |
| Open a list | Its HTML already contains the visible table and assumptions; shared CSS and a small optional script are separate assets |
| Next table page | Another bounded static HTML page for that same list |
| Open a record | A standalone HTML page with its notes, source locations, selected earlier references and BibTeX |
| Browse a problem | Paginated HTML containing only that problem's variants |
| Download data | Explicit `.bib`, per-list JSON/CSV, individual record JSON or the canonical data ZIP |

The common script adds current-page filtering, category navigation and old query-string redirects. It contains no `fetch`, runtime data dependency or global catalogue. The separate History comparison script requests compact static history data only when used. Basic reading and navigation work without it. File URLs are relative, including CSS, SVG record links and downloads; the link check resolves all of them beneath a GitHub project prefix.

## Bounds and generation

Tables have at most 100 rows and target at most 64 KiB of row markup. The whole HTML page also includes the shell, comparison rules and chart. One exceptionally long row may exceed the row-markup target; source field lengths and author counts are validated. Definitions are kept with their comparison list, not repeated as an enormous global category tree.

Charts are now on the separate History page. The older per-category history URLs retain paginated static views, which carry the preceding point across a page boundary. All segments use horizontal/vertical SVG commands, so a new bound never improves an earlier date by interpolation. Ties and alternative memory points remain in the table without creating fictitious historical improvements.

Grouping is linear in records/categories; sorting is per list. Rendering cost follows the amount of generated content. The generator streams output files rather than retaining the entire generated website in memory. The canonical-data ZIP compresses one editable file at a time, retaining only its central-directory metadata. Editable source chunks are independent of HTML pagination.

Every local build recalculates the lists from source, then skips writes whose content hash is unchanged. Deleted or renamed outputs are removed. Standalone record pages have no global totals/build timestamp that would otherwise invalidate every record after an unrelated addition. Fresh CI runners still perform complete builds. The output directory is generated state: do not edit it manually.

`SOURCE_DATE_EPOCH` makes the release date reproducible; Actions sets it from the source commit. The build report records bytes, file counts, write counts and elapsed time. Publication fails if the generated site exceeds 1,000,000,000 bytes, rather than publishing a known oversized Pages artifact.

### Synthetic large collection

`npm run benchmark:static -- 100000 1000` generated 100,000 synthetic rows over 1,000 lists, using one shared paper. The counting sink discards output after measuring it; this is a renderer/serialization benchmark, **excluding filesystem writes, source ZIP generation, upload and network latency**. It is not a benchmark with 100,000 independent papers.

| Synthetic measurement | Result |
| --- | ---: |
| Generation time | 12.3 seconds |
| HTML + generated download files | 205,030 |
| Generated bytes, excluding root-added assets/source archive | 971,951,195 |
| Largest list HTML | 72,240 bytes |
| Largest list HTML, gzip measurement | 3,845 bytes |
| Largest source-detail page | 5,482 bytes |
| Heap used at end, not a peak measurement | 104 MiB |

This identifies the real tradeoff: reading one small list stays independent of total database size, while offline output and deployment still grow. This 100,000-row fixture already approaches the Pages size ceiling before source archives are added. Many thousands of entries are a comfortable use case; claiming unlimited scale on GitHub Pages would be misleading.

At larger sizes, keep table/history pagination, put bulky attachments outside the site, move whole-database archives to repository release assets, and consider dropping duplicate individual JSON exports in favor of the already available per-list JSON. If file count or published bytes remain limiting, another static host can serve the identical generated output. A database server is not necessary just because editing is shared.

## Community operations

A central `.bib` plus modular list JSON is manageable because reading is far more frequent than editing. Reviewers see readable source diffs; generated HTML is not committed. Separate topic files reduce conflicts and allow review routing to experts. The shared bibliography can become an editing hotspot: sort entries consistently and keep changes small. If concurrent edits become frequent, extend the loader to topic `.bib` shards and generate the single bibliography download from them; never maintain two authoritative copies.

Protect the default branch, require successful validation/build and documented subject review, and keep code/workflow changes under maintainer review. CODEOWNERS provides review routing, not directory-scoped collaborator permissions. See [the operational setup](COMMUNITY.md) for exact controls and official references.

GitHub currently documents a 1 GB published-site limit, a 10-minute deployment timeout and soft bandwidth limits. Custom Actions publishing is exempt from the soft 10-builds/hour limit; other limits still apply. See [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

The old JSON compiler remains available for regression/export tests; its `npm run benchmark` is not a measurement of the active HTML route. Use `benchmark:static`, `outputs/build-report.json` and `npm run check:output` when assessing the published architecture.

## Version 8 presentation update — 9 November 2026

The restyle uses local Arial/Helvetica/system fonts, a compact header/topic sidebar, problem pages and category controls. It adds no library, external font request, runtime database or data fetch. The scientific source data is unchanged. The current stylesheet is about 28 KB and the enhancement script about 2.2 KB. A complete local build remains under one second for the current collection; the largest list HTML is about 32 KB. The version 7 measurements above remain historical measurements, including the synthetic benchmark; they are not a rerun of the revised page shell. Hosting/output limits continue to apply.

## Version 9 history comparison

The category tabs duplicating the selector were removed. Each leaderboard has one selector and a link into the global History page. Comparison JavaScript is loaded only by that page, while small history JSON and paginated problem-specific category indexes are generated offline. Selecting two lists does not fetch all rows, papers or all categories. Histories preserve their own strict improvements and are grouped by cost normalization instead of taking a minimum across unrelated categories. Detailed source records continue to live on their own precompiled pages.

## Version 10 other-result markers

The collection now includes relevant non-record bounds. Strict improvements still define the step lines; other eligible numerical results have separate event chunks and diamond markers. Event chunks contain at most 100 points and target at most 64 KiB. The explorer requests only the selected categories and chunks overlapping the displayed dates, in batches of four; its request cache holds at most 32 entries. Turning off **Show other results** skips event fetching and excludes those markers from the axis range.

The default HTML comparison limits embedded histories and events to a recent window if either becomes large. At most 240 other-result markers per category are rendered, with a visible count and a link to the full static result list when sampling is needed. All selected points are used for the axis when loaded; narrowing the date interval retrieves that interval's events. The cost of a single result list remains independent of these optional history requests. Canonical BibTeX/JSON and full result downloads preserve all entries.
